Automated Invoicing & Expense Tracker

A web application written in Python that lets a small business manage customers, raise GST-style invoices with PDF export, record expenses and read profit-and-loss reports. It runs on Railway with a PostgreSQL database and works on laptops, tablets and phones.

  • Language: Python 3.12
  • UI: Streamlit
  • Database: PostgreSQL (SQLite locally)
  • Hosting: Railway
  • Code: 5 modules, 1,711 lines
  • Report date: 11 Nov 2026

01Overview

The app replaces spreadsheets and paper invoices for a freelancer or small shop. It has seven pages: Dashboard, Reports, New invoice, Invoices, Customers, Expenses and Settings.

The starting point was a single-file Streamlit prototype (app.py, about 450 lines). It stored data in JSON and CSV files, supported one item per invoice, and had no deployment configuration. When it was deployed to Railway it did not start. This version restructures it into separate modules, adds a real database, adds the missing features, makes the layout responsive and fixes the deployment.

02Architecture

The browser talks to one Python web service on Railway. The service is split into a UI layer, a storage layer and two helper modules. Only the storage layer talks to the database.

A request flows like this: Railway sets the PORT variable, start.py starts the Streamlit server on it, and every page in app.py reads and writes through functions in db.py. Sample data and Amazon imports are converted by sample_data.py and then saved through the same db.py import function.

Business rules

  • Invoice numbers are sequential (INV-1001, INV-1002, …) and are generated inside the same database transaction as the insert, skipping any number already used.
  • Totals: subtotal = Σ qty × price; tax = Σ qty × price × tax% ÷ 100; total = subtotal + tax − discount, with the discount capped so the total never goes negative.
  • A Pending invoice whose due date has passed is shown as Overdue. This is calculated when displayed, so it is always current.
  • Income counts only Paid invoices; Cancelled invoices are excluded from billed totals.

Responsive design and security

  • Custom CSS media queries: above 1024 px the layout uses full rows of columns; from 641 to 1024 px (tablet) columns wrap two per row; at 640 px and below (phone) everything stacks in one column with full-width buttons. The sidebar menu folds into a button on small screens.
  • Framework menus, the deploy button and the footer are hidden so the app looks like a standalone product.
  • Optional login: if the APP_PASSWORD variable is set, a sign-in screen appears. The password is compared with hmac.compare_digest to avoid timing attacks.
  • All database writes use SQLAlchemy parameterised statements, so user input cannot inject SQL.

05Database design

Four tables are defined once in db.py with SQLAlchemy Core and created automatically on first start (metadata.create_all). The same definitions work on PostgreSQL and SQLite.

TableKey columnsPurpose
customersid PK, name, email, phone, company, tax_id, address, created_atClient records
invoicesid PK, number unique, customer_id, customer name/email/address snapshot, issue_date, due_date, status, items (JSON), discount, subtotal, tax, total, notes, paid_dateInvoices; line items stored as a JSON list
expensesid PK, date, category, vendor, description, amount, payment_methodSpending records

Customer details are copied onto each invoice when it is created, so an old invoice still shows the address it was issued to even if the customer is later edited or deleted. Line items are kept as JSON because they are always read and written together with their invoice.

06Data sources

The app holds the user's own data. For demonstration it can load a realistic sample dataset, and real Amazon sellers can import their own orders.

Sample dataset: DummyJSON API

Clicking Load sample data fetches two endpoints from DummyJSON, a free public test-data API for e-commerce apps. No key is needed.

EndpointGivesBecomes
GET /users?limit=0Names, emails, phones, addresses, companiesCustomers
GET /carts?limit=0Shopping carts: products, quantities, prices, discounts, user idInvoices (one cart = one order = one invoice)

The conversion steps in sample_data.py are:

  1. Prices are converted from USD to INR at ₹83 per dollar when the currency is ₹.
  2. Orders are spread across the last 12 months.
  3. Statuses follow a realistic pattern. About 4% are cancelled. Orders older than 45 days are mostly paid (92%), and newer ones are about half paid.
  4. Twelve recurring business expenses are generated monthly or fortnightly: rent, salaries, utilities, software, ads, shipping, packaging and GST. They are scaled so the costs come to about 65% of revenue, giving a profitable demo business.
  5. Every sample record's id starts with sample-, so Remove sample data deletes exactly those records and nothing else.

If the API cannot be reached, the app uses a built-in generator instead: 40 Indian customers in 10 cities, 180 orders from a 26-product catalogue with INR prices, and the same expense pattern. A fixed random seed (42) means the demo looks the same every time.

Real data: Amazon Seller Central import

Why not an Amazon API?Amazon has no public API that returns customer data, for privacy reasons. The Selling Partner API returns only a seller's own orders and requires a registered developer app with OAuth credentials. The Product Advertising API returns catalogue data only and requires an approved Associates account.

Instead, a seller downloads the All Orders report from Seller Central (Reports → Order Reports, a tab- or comma-separated file) and uploads it in Settings. The importer:

  • reads columns such as amazon-order-id, purchase-date, order-status, product-name, quantity, item-price, item-tax, buyer-name and ship-city
  • groups rows that share an order id into one invoice with several line items
  • works out the tax % from item tax ÷ item price, and subtracts promotion discounts
  • maps Shipped to Paid, Pending or Unshipped to Pending, and Cancelled to Cancelled
  • gives each order a stable id, so re-uploading the same report does not create duplicates

07Deployment on Railway

Railway builds and runs the app straight from the GitHub repository. Every push to main triggers a new build and deploy.

Steps

  1. Create the service. New Project → Deploy from GitHub repo → Automated-Invoicing-Expense-Tracker, branch main.
  2. Build. Railway's Railpack builder detects Python from requirements.txt and .python-version (3.12), then installs the packages with pip.
  3. Add the database. New → Database → PostgreSQL. Railway creates a managed Postgres service in the same project.
  4. Connect them. On the app service, under Variables, add DATABASE_URL = ${{Postgres.DATABASE_URL}}. This is a reference variable, so Railway fills in the real connection string.
  5. Start. Railway runs the start command from railway.json: python start.py. This starts the server on 0.0.0.0:$PORT.
  6. Health check. Railway requests /_stcore/health and sends traffic only after it answers ok (timeout 120 s). If the process crashes, it is restarted up to 5 times.
  7. Public URL. Settings → Networking → Generate Domain gives a free *.up.railway.app HTTPS address. Its target port must match the port shown in the deploy log.
  8. First run. The app creates its tables in Postgres automatically. The sidebar shows Storage: PostgreSQL.

08How it was built

The work followed the order below. Development was done with Claude Code, an AI coding assistant, which wrote and tested the changes from my requirements. I then reviewed, deployed and checked the results on Railway.

  1. Analysed the prototype: one 450-line file, JSON/CSV storage, no deployment config. Identified why Railway could not start it.
  2. Designed the storage layer (db.py): table definitions, PostgreSQL/SQLite switch, create/read/update/delete functions, invoice numbering, backup and restore, migration of old files.
  3. Rewrote the PDF generator (pdf_utils.py) with a business header, bill-to block, items table and totals.
  4. Rebuilt the UI (app.py) as seven pages with grouped navigation, Plotly charts, editable grids and responsive CSS.
  5. Added the data features (sample_data.py): DummyJSON loader, offline generator and Amazon order importer.
  6. Added deployment config: railway.json, Procfile, .python-version, Streamlit config, then start.py.
  7. Tested locally against SQLite and a real PostgreSQL 16 server, and in a headless browser (section 9).
  8. Deployed: pushed to GitHub, merged to main, connected Railway Postgres, generated the domain.

Run on your own computer

git clone https://github.com/pats-speedlark/Automated-Invoicing-Expense-Tracker
cd Automated-Invoicing-Expense-Tracker
pip install -r requirements.txt
python start.py          # then open http://localhost:8501

To use PostgreSQL locally, set DATABASE_URL=postgresql://user:password@localhost:5432/dbname before starting.
